# bidvolt 企业资料库摸底（资产盘点）

## 触发条件
用户要求：全面摸底/盘点 bidvolt 企业资料库、产出「企业事实清单+可装订证据清单」、分析当前项目响应供应商的企业资料（营业执照/资质/业绩/人员/财务/信用/专利/绿证等）。此类任务通常发生在 gap-report 或 bid-generate 之前：先摸清"有什么可用证据"，再谈差距与写作。

## 数据源层级（按成本从低到高，决定调用策略）
1. **list_assets**：全量资产清单（asset_id/name/asset_type/category_id/source_file_id/image_described）。无分页参数，全量返回可能 300KB+，服务端自动持久化到 `/tmp/hermes-results/call_*.txt`——不要读原始输出，直接用 python 解析（见 scripts/group_assets.py）。
2. **get_asset(asset_id)**：返回 `image_description` 结构化字段（dates/people/stamps/amounts/numbers/subject/doc_type/text_summary）+ facts。**这是批量盘点主通道**——资质/合同/专利/证件全部先走它，绝大多数条目不需要 vision。
3. **vision_analyze_minimax(file_id=source_file_id)**：仅用于关键证据复核：营业执照全字段、统一社会信用代码逐字、合同签署页乙方名称/盖章、主体存疑文件（关系说明/承诺函/落款遮挡件）。
4. **download_project_material(file_id, save_path)**：html/md/pdf 等文本类资产拉本地直接读（比 vision 便宜且精确）。**目标目录必须先 mkdir -p，否则 Errno 2**。

## 标准流程
1. **全量拉取+分组**：list_assets 一次拉全；解析后按路径段分组（一级段=资料类别；项目段=00_共享原件/各项目子目录/各项目子目录/03_本项目…/04_福建/99_敏感材料），写 `assets_full_listing.txt` 供 grep 定位。
2. **证据源优先级**：00_共享原件（最干净原件）→ 当前项目目录 → 99_敏感材料（财务审计/身份证/社保/合同原件，只列清单不展开敏感字段）。
3. **合同批量取证**：同一项目合同页 asset_id 连续（如 1.1→753-757，1.2→758-761…），逐份 get_asset 首页拿合同名/甲乙/日期/编号；**金额在费用条款页（中间页）的 amounts 字段**，不必逐页 vision。
4. **资质/专利/软著/人员/社保/财务/信用**：逐项 get_asset，记录 编号/发证机关/有效期/主体。财务审计页数≈该年份资产数（2023/2024/2025 各 24-28 页，首尾页 get_asset 确认事务所与文号即可）。
5. **文本资产本地读**：先 mkdir -p 再 download_project_material（公开来源 html/md、企业基本情况表 pdf 常有电话/股东/人员统计等加分事实）。
6. **关键交叉核验**（见 Pitfalls）：信用代码、盖章主体、专利权利人、证书有效期、名称变更。
7. **产出 analysis_assets.md**（模板：templates/analysis_assets.md）：①企业主体事实表 ②资质清单 ③业绩清单（可装订） ④人员清单 ⑤财务/信用 ⑥其他评分证据 ⑦可装订性评估（逐条标注）。

## 可装订性判定规则
- **主体一致**：asset 的 subject/信用代码 == 投标主体。改名前的旧名称合同（如"北京爱图客科技"）需附名称变更通知佐证才能装订。
- **有效**：以项目截止日逐证核验有效期（实战例：ISO27001 证书 2026-01-10 到期，项目当年 9 月投标即已过期，不可装订）。
- **相关**：技术开发/技术服务类 > 咨询/外包类，匹配评分口径。
- **完整**：合同+发票+发票查验截图三件套；缺发票/查验的合同标"证据不完整"。

## Pitfalls（实战踩坑）
- **OCR 公司名变体不可信**：扫描合同乙方名称被读成"网客未来/控客未来/奥客米/图鉴未来/国泰未来/阳客来来"等——全是"图客未来"的误读。判定主体以**统一社会信用代码 + 银行账号**（如 11001117300052507773）为准，不要信名称字段。
- **信用代码首次 vision 可能误读**（实战：读成 91110111MA81K7964Q，真实为 91110111318157964Q）：用 gsxt/信用中国/合同签署页/响应供应商基本情况表多源交叉确认，必要时二次 vision 只问代码逐字。
- **MCP 连续失败冷却**：连续 4 次失败后出现 "unreachable, auto-retry in ~Xs"——**立即停止一切 MCP 调用**（每次调用都会重置倒计时），转做本地工作（整理 notes、起草 md、sleep 45s+），再 health 确认后重试。
- **模板文件可能混入他人盖章件**：关系说明/承诺函等格式化文件要逐个 vision 复核盖章主体，"投标人"栏与盖章公司不一致即标记不可装订（实战：1254 关系说明盖章为另一公司）。
- **专利权利人未必是本企业**：库内"专利证书"扫描件可能是受让前旧权利人（实战：CN212323461U 权利人为南京网为，主体不符不可装订，需转让/授权依据）。
- **合同段可能缺发票**：逐合同核对三件套，缺的标不完整（实战：1.20 无发票/查验）。
- **历史项目复用件**：其他项目目录下的业绩/资质是复用件，可作补充，但优先用共享原件+当前项目目录，避免跨项目主体错配。
- **合同签署页 OCR 最不可靠**：盖章压字/扫描模糊导致名称乱码，但同页的信用代码、账号、开户行通常是可信锚点。

## 支持文件
- templates/analysis_assets.md —— 摸底产出模板（7 张表结构）
- scripts/group_assets.py —— 解析 list_assets 持久化输出并按（项目,类别）分组（项目段标记按库内实际目录微调）
