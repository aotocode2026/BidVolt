# 成果独立验收（撰写验收）

本 Skill 是投标工作台「验收门」：站在**招标人能不能直接拿这份文件去投标**的角度，
对已落库的三份成果做只读核验，产出逐条验收报告。写的人不验收自己写的东西——本角色独立于生成/校核/评标。

## When to Use

- 用户要求「独立撰写验收」「独立验收」「核验三份成果是否达标」
- 主流程 E 阶段派「验收子 agent」时（bidvolt-agent-pipeline 的校验/验收角色）
- 用户明确说「你只负责核验，不负责修改」这类纯验收请求
- 用户要求「评标专家视角评审最终交付件」「F 阶段评审」「打开 zip 实读评审完整性/响应度/报价/风险/成品纪律」时（主流程 F 阶段，五维框架见 Pitfalls 首条）

## 唯一目标

判断一句话：**「招标人拿到这份交付件，能不能直接去投标？」** 所有核验项都服务于这句话。

## 核验框架（六项，逐项过/不过）

1. **业务字段一致性**：三份成果的 `buyer`/`supplier_name`/`project_name`/`tender_no` 必须完全一致，
   且与项目事实（分标编号、包号、最高限价、履约期限）一致。任一关键字段不一致 = 阻塞（先修再谈验收）。
2. **技术标实质响应**：读**全量**技术规范书（get_project_material_blocks 遍历全部 block，别只看首页），
   逐章节核对技术标是否实质响应（有正文、非目录、非一句话概括），尤其五大模块/架构/功能/人员/成果验收质保/支付/知识产权。
   **人员表必须与商务标团队表逐人比对**：商务标已填实而技术标表1/表2留【待补充】=跨成果不一致+本可填实=阻塞（技术评分「项目团队」动辄12-20分直接空转；资料库有人员证件素材即构成可填实证据，project 187 实测）。
3. **商务标覆盖**：授权委托书、商务偏差表（必须含「无偏差」声明）、响应保证保险/保证金、补充文件各子节。
   **授权委托书必须成文于成果本体**——中间矩阵/工作记录声称「由他方/主会话另行成文」不算数；project 188 实测：D2 矩阵称外置成文、三份落库成果均无该主条目=阻塞（主条目缺失+未按格式签署属否决红线相关）。
   核对「本项目免收保证金」类声明是否与采购文件一致。
4. **报价单格式**：`sheets` 必须是**数组的数组**（每行是数组，不能是对象/带 item 键）；含最高限价约束；
   金额未知处标【待补充：具体标签】，不得整表省略；无真实成本依据不得编造数字。
   **备注栏检查**：不得出现内部测算口径/元语言——「建议报价」「行情样本/公开中标价区间」「检索日期」「请客户确认调整」等文字随备注直接提交招标人，出现即阻塞（project 187 实测）；备注只允许对外口径（无最高限价说明、采购代理服务费口径、税率说明）。
5. **【待补充】守则**：逐条列出全部待补充，检查是否有裸【待补充】或「具体标签」模板字样；
   检查是否有「本可填实却待补充」（能从采购文件/企业资料库/公开渠道取得却留空的）。
6. **提取完备性抽查（B 步骤验收门）**：list_requirements 是否覆盖 资格要求(通用+专用)、评分标准(技术ZHFWJS01/商务FWSW01)、
   模板清单(get_template_outline)、否决条款(reject_clause)。有明显缺口要列出。
   B 步骤验收的完整六子项判据（①资格 ②评分 ③模板 ④否决 ⑤基础事实 ⑥坐标质量）、project 181 req_id 事实落点地图、
   ①每条判据对照材料原文 diff（get_project_material_blocks 逐块核对），条目存在 ≠ 内容正确；
   ②**主会话声明 ≠ 落库**——「已补坐标/已修正」一律 re-fetch get_requirement 验证实际状态
   （4275 声明补 272 b1220，实际 coordinates=[]，坐标实际落在另一条 4460）；
   ③坐标抽样（条数按覆盖面由你判断），block_id 逐一回溯材料原文（分页 offset=(page-1)*size）。
   **本项目 C 验收补丁**：B 报告对坐标所引 block 内容的解读可能与实读原文不一致——B 报告称 b166082「目录注脚」实测为 JS-ZHFW01 模板表头（166083 才是注脚）。C 验收对 B 报告中的「坐标 + 文字摘录」段**不能照抄当作内容核对证据**，必须 re-fetch get_project_material_blocks 实读逐字比对；B 报告自述与 MCP 实读不符 = 一般级缺陷，不影响坐标真实性（坐标仍真命中），但报告要点名「建议 B 报告 §X.Y 修正 b166082 内容描述」。合并归档到 pitfall「坐标存在且形态合法 ≠ 指向正确」——本项目 实测是 B 报告**坐标指错段落**，本项目 是 B 报告**坐标对但文字摘录写错**（同一变体）。
   **doc_template 同 order 双轨 bug 检测（本项目 C 验收补丁）**：B 首轮落 8 条长标题 doc_template（首行 21-79 字，不合规）+ 主会话补落 8 条短标题（合规）= 同 order 2 条并存，对 G 装订清单双轨映射干扰。**C 子 agent 必查**：8 条 doc_template 同 order 有 ≥2 条 = 双轨 bug，判**一般级**（不阻塞），建议主会话 B 阶段 update 同 req_id（content 第一行改为 ≤24 字干净短标题 + structured.is_file_item=true）而非新建并存条目。B 报告声明「作 is_file_item=false 噪声保留不删不修」前必须评估下游消费端：`get_template_outline` 只返回 is_file_item=true 的 8 条做 slice 定位——长版不影响切片；但写正文时若用 `list_requirements` 拿全部 doc_template 条目（16 条），按 order 双轨映射易错。

## Procedure

1. 先建 `todo` 列六项核验计划（可选，多步骤时建议）。
2. 并行取基线数据：`list_requirements`（可能被截断，配合 get_requirement 逐 id 探测）、
   `get_template_outline`、三份成果 `get_deliverable_content`、`list_project_materials`。
3. 定位本包事实：在采购公告附件「分包表/专用资格表」（见 Pitfalls #3）里找到本包号那一行，
   锁定 分标编号/包名称/最高限价/履约期限/实施地点/专用资格要求。
4. 读全量技术规范书 + 采购文件评分/否决章节，与三份成果逐一比对。
5. 逐条输出验收报告：**过/不过 + 问题清单**。每条问题带【定位（文件/章节/坐标）】【严重度：阻塞/一般/提示】。
6. 最终结论只写「过」或「不过」+ 未闭环项，不落库、不修改任何成果。

## Pitfalls（实战验证，必看）

- **自设指标冒充采购约束（最常见且最隐蔽）**：技术标可能把采购文件中**根本不存在**的性能指标
  （如边缘时延≤100ms、预测MAPE≤8%/15%、等保三级、多协议IEC61850/Modbus/DL645/OCPP/MQTT/HTTP、
  国产化信创、可用性≥99.9%）写成「关键约束/技术约束」。**必须 diff**：技术标声明的指标 vs 技术规范书原文。
  原文没有的一律判为「应答人自设承诺」，非采购要求——不算错误，但可能误导评标、埋履约/澄清风险，
  要提示改成「应答人响应承诺（优于采购要求）」措辞并确认企业确有兑现能力。判断依据只有技术规范书原文
  （如项目只有 GB/T 25000.51-2016 标准 + 「秒级响应」，就没有这些具体数字）。
- **专用资格要求藏在独立表格**：专用资格要求（如「自2021-01-01起具有信息系统开发业绩」）在
  **采购公告附件的「专用资格要求」表**里，不在采购文件正文。提取时可能只落一条「详见采购公告附件」指针
  （req 内容笼统），漏掉具体业绩/资质要求。验收要读这张表，确认具体专用资格是否被提取、成果业绩是否满足。
- **源材料内部矛盾要标注而非静默选边**：如「实施地点」采购公告附件表=北京市、技术规范书§1.2=杭州市。
  成果统一采用其一 + 主动标注矛盾说明理由 = 正确处理；但要提示成交前向采购代理书面澄清确认，避免被判「理解偏差」。
  注意技术规范书常有兜底条款「与本规范书不一致的以本规范书为准」。
- **混合税率 = 否决风险**：报价单某行标「6%/13%」混合税率会被判「税率异常=否决」。软件/服务统一6%、
  硬件统一13%，拆行或每行标单一税率。采购文件明确「不按国家规定税率填报税率/税率异常=否决」。
- **二选一模板字样**：「一般纳税人/小规模纳税人」这类标签算含混；若正文已写「一般纳税人」又标二选一
  = 自相矛盾，属「本可填实」（可从企业资料/公开渠道确认）却留空。
- **list_requirements 可能被截断**：返回体量大时用 get_requirement 沿 req_id **连续探测**类型分布
  （qualification / score_rule / reject_clause / technical_spec / commercial_clause / contract_clause / doc_template
  各有区间），据此判断提取是否完备，别只看列表开头几十条。
- **项目事实以技术规范书为准**：采购公告附件分包表与技术规范书冲突时，技术规范书通常有最高优先级条款。
- **python-docx 读不到修订插入，绝不能据此判空（实战教训）**：python-docx 的 `Paragraph.text`/`cell.text` 只遍历直接子节点 w:r，**w:ins/w:del 包裹的修订内容完全提取不到**。验收时表格显示全空 ≠ 产物空白——project 181 实测：报价明细表/技术偏差表/专项响应文件的全部内容都在 w:ins 修订里，曾被误判为空文件。必须用 lxml 遍历全部后代 w:t（含 w:ins）核对，用 `scripts/inspect_docx_deep.py` 一键深挖（修订插入/删除文本、批注、表格逐格实况、每处【待补充】上下文）。
- **授权委托书「括号标签无空位」边界**：模板原文若为「特授权＿代表我方全权办理…（采购编号）（分标编号）（包号）项目」，标签后无冒号+空位时 fill 的 values 打不到 → **关键编号可能「未填实值也未标待补充」**。验收必须逐字核对这类括号标签位。实测案例：授权委托书三处编号均未回填 = 该文件不能直接投标，列为阻塞。修复姿势：裸括号标签用 fills 逐个定向替换（find「（采购编号）」→「（采购编号：＜本项目值＞）」，同理分标编号/包号），回填后 inspect 逐字确认仍在。
- **matched_title 为空 ≠ 产物缺陷（重建切片）**：slice located=false 的条目（project 181 实测 4522 技术偏差表/4523 专项响应文件——底稿定位器对技术文件章标题匹配失败，272/277 均失败）按解析清单重建切片，seal 回执 `matched_title=""`，但 package audit 实测 `identity_ok=true、identity_issues=[]`。验收以 inspect_agent_artifact 实际内容 + 源成果 get_deliverable_content 对照为准（重建切片内容靠 append 补齐：偏差表含项目信息行+无偏差标注+逐条项核对清单；专项响应文件含技术标全部实质章节），**不因 matched_title 为空判阻塞；但必须核实这两份正文完整（不能只有标题），并核对 audit 未出现 identity_issues**。
- **「已填值+待补充标签共存」形态**：fill 机制可产出「单位地址：北京市海淀区…【待补充：单位地址】」这种值+标签并存文本（值插入空位但标签词残留）。验收要逐条列出，提示客户清理标签；残留过多会让文件显得未完成。
- **zip 响应包内混入内部会话记录 = 硬伤**：package_response_zip 自动附「会话记录/主会话记录.md」+「会话记录/主会话记录-精简版.md」**两份**（某任务 实测 12 entries，3.4MB+778KB），含成本测算/谈判策略。投标包绝不能含这些文件（泄露内部决策 + 国网查重红线）。验收必查 zip 清单（unzip -l / inspect_agent_artifact），**两份都要**列入「剔除后再投」。
- **xlsx 合计单元格可能为 None**：build_quote_xlsx 的「响应总价（含税）」=SUM 替换在个别版本未生效（合价格空值、仅备注文字）。验收用 openpyxl data_only=False 读合价单元格，确认有公式或数值，不能只看各行分项自洽（project 181 实测 D19=None 而 8 分项之和=190 正确）。
- **xlsx 三联缺陷 = 阻塞（本项目 实测，三合一打包判级）**：合并自 181/192 后**第四次**出现的 xlsx 报价单缺陷形态，但 本项目 同时踩中三个独立缺陷叠加，必须都查：①合计行 col8 含税合价 = `None`（缺 =SUM 公式 + 缺字面量 历史轮报价（不沿用） + 仅备注列文字说明 历史轮报价（不沿用））②三行分项之和 ≠ 合计行（实测 31+25.49+1=57.49 ≠ 58.49，差 1.00；含税口径 32.86+27.02+1.06=60.94 ≠ 历史轮报价（不沿用） 差 1.06）③**数字单元格全字符串类型**（`'31'`/`'32.86'`/`'1'`/`'58.49'`/`'历史轮报价（不沿用）'`，`type=str` 而非 `int/float`——Excel 公式无法生效、按数字排序失效、openpyxl 改值需强制 `cell.value = float(x)` 重写）。**触发原因**：build_quote_xlsx 服务端组装 sheets 时把所有数值走 `str()` 化路径，导致 sheet 字符串污染合计公式与分项校验。**验收必查动作**（本项目 E 验收实测，全套 5 步）：1) `dump_artifacts_from_db.sh <pid> <artifact_id>` 导出封存字节（不能信本地文件，MCP inspect 报"rows=5"看似齐全但合计行 col8=None 不显示）；2) openpyxl `data_only=False` 读 row=N col=8 验值非 None；3) **逐行验算 Σ不含税=合计** 与 **Σ含税=合计** 两个口径；4) `cell.data_type` 检查所有数字单元格 = `n`（number）而非 `s`（string）；5) `cell.number_format` 检查非 `General`（建议 `0.00` 或带千分位）。**判定**：任一项不通过 = 阻塞；合计 ≠ Σ分项 = 触发"算术错误=否决"红线（材料 1819 block_id 166 600）。修复建议（G 阶段 15 分钟）：①三行分项改精数（31.49/26.00/1.00 与 docx 报价明细口径一致）；②合计行 col8 写 `=SUM(H2:H4)`（服务端会自动替换）/ 或字面量 `历史轮报价（不沿用）`；③字符串类型转数值 `cell.value = float(cell.value)` 重写并 `cell.data_type='n'`。**MCP `inspect_agent_artifact` 不暴露 None 缺陷**——只显示 `rows=N cols=M` 不显示单元格值；预览只显示前几行。**dump + openpyxl 逐格**是必经路径。
- **「封存 zip 引用陈旧字节」= 阻塞（本项目 final E 验收实测，最隐蔽的一类）**：E 验收必须以**封存 zip 内的字节**为事实源（招标人拿到的是 zip，不是本地副本），但 181/192/199 都出现过「本地文件已修，但 `package_response_zip` 封装的还是修前的旧版本」的内容漂移问题。**触发机制**：`upload_deliverable_file` 覆盖上传 artifact 后，主会话可能**没有**重新调 `package_response_zip`，或主会话另起一轮时只重写了本地 docx 而忘记再次 seal+zip——结果是 PG 里 `agent_artifact` 的字节是新版，但同一份文件被早期 zip 引用并冻结。**本项目 final 实测形态**：本地 `/data/hermes/work/project199/final/（二）报价明细表.docx` 38017 字节已清洁（无成本法/无反算），但封存 zip 668 内 `价格文件/（二）报价明细表.docx` 仍是 38791 字节含 §二成本法 + §三行情样本 5 条具名 + §四反算 + §五尾差吸收说明 + 成交人（公开成交公示，非本企业）成交 5 条同业报价；同样的现象出现在 9 份 docx 中的 7 份（仅补充文件 659 md5 一致）——本地文件 mtime 04:37-04:45，zip 668 created_at 04:40:34，zip 引用了 seal 时点的旧字节。**MCP `inspect_agent_artifact(zip_id)` 只列 zip namelist + 各 entry 的 bytes，不揭示 zip entry 与 `agent_artifact` 当前字节是否一致**。**验收必查动作**（E 验收的强制 5 步，缺一不可）：
  1. `inspect_agent_artifact(zip_id)` 拿 zip 完整 namelist + 每 entry 字节数
  2. **逐 entry 用 python zipfile 从 zip 内抽出，与 `agent_artifact` 当前 bytea 比 md5**（不是与本地 `/tmp/p<项目>/final/` 比——本地不是事实源）；md5 不一致 = zip entry 是旧版本 = 内容漂移 = **阻塞**
  3. 顺便对照本地 final 副本三处：本地 ≠ zip ≠ agent_artifact 三层差异定位「哪一层是当前真值」
