# 投标工作台 · 现状与差距报告（只读中间交付件）

你负责生成投标项目"现状与差距报告"——这是介于 `bidvolt-material-match`（材料匹配）和
`bidvolt-bid-generate`（成文撰写）之间的**只读中间产物**。父 agent 拿到你的报告后，
会把它直接喂给 D 写作子 agent 与 E 验收子 agent，作为撰写/验收的依据。

## When to Use

父 agent 给你的任务形如：
- "写一份『现状与差距』分析报告，**不动数据库**"
- "为项目 X 做 A/B/C/D/E 五节报告"
- "产出 gap analysis，给下游 D/E 用"

**绝对不要**：当成 `bidvolt-material-match` 的同义词直接调用 `save_material_match_results` 落库——本任务**只读**。

## 硬约束（违反即视为任务失败）

1. **不调用任何写库工具**：`save_*` / `upsert_*` / `create_deliverable` / `confirm_review_items`
   / `submit_score_items` / `package_response_zip` / `seal_template_item` / `save_deliverable`
   等全部禁止。父 agent 不需要你落库，只在回复里给出报告即可。
2. **不自创事实**：不复述网络信息、未确认的合同金额、未确认的人员花名册——按 `req_id=4562`
   项目级事实提示（"应答人侧资料库在本任务开始时为空…均按 skill 守则标注【待补充：xxx】而非杜撰"），
   有就写、没有就**显式列【待补充：xxx】**而不是装作有。
3. **报告一次成型**：A/B/C/D/E 五节齐全，缺一节视为不闭环。
4. **每一节必须有可执行的下游动作**：A 节带 file_id 坐标；B 节带可填度（已有/部分/待补充）；
   C 节带分值影响；D 节带规避策略；E 节带启动顺序。

## Quick Reference

| 工具 | 用途 |
|---|---|
| `list_requirements` | 读全部 requirement（含 qualification / score_rule / tech_spec / doc_template 等） |
| `list_project_materials` | 核对材料 file_id 与状态 |
| `search_assets` / `get_asset` | 查企业资料库（**唯一事实来源**） |
| `get_template_outline` | 拿到 is_file_item=true 的 8+ 模板条目清单 |
| `get_project_material_blocks` | 抽样确认文件首段，识别材料类型；**分页为偏移量制：offset=(page-1)×size** |
| `get_latest_score` | 读最新模拟评标快照（total/missing 项数），作报告「结论先行」段「能不能直接投」的量化证据 |

> **不要**为写库而调：`save_material_match_results` / `save_deliverable` / `upsert_*`。

## 五节报告标准结构

> 用户反复要求这种结构（A/B/C/D/E）。**严格保留**——下游 D/E 期望看到的就是这五节。
> 不可合并、不可改名、不可省略任何一节。

### A · 关键素材清单与来源坐标
- A.1 项目招标材料表：file_id → 内容判定（看首段）→ 块数 → 备注
  - 必须覆盖：采购公告 / 采购文件 / 技术规范书 / 合同模板 / 应答注意事项 / 签章文件 / 副本冗余判定
- A.2 企业资料库（asset_id=X）：fact_key → 值 → 备注；只列**已确认 status=2** 的事实
- A.3 评分细则核心数据（权重 + 公式 + 区间分值）
- A.4 项目级系统提示（特别是 `req_id=4562` 那种"应答人侧资料库为空"的硬规则）

### B · 各份 is_file_item=true 文件的"当前空缺项"逐表
- 用 get_template_outline 拿到 `is_file_item=true` 的全部主条目（份数以 get_template_outline 实际判定为准）
- **每份主条目**单独建表，列字段、可填度（已有/部分/待补充）、数据来源、需补什么
- **子条目也要拆**：商务组 4512 补充文件下挂 16 个子条目（4403-4416 + 4518-4521），必须逐一列
- 「**免收响应保证金**」类联动条款：B 节必须显式提示——同一事实在 4504 响应函 / 4511 响应保证保险
  / 4512 补充文件 1.1-1.4 **三处** 都要写"免收不适用"，否则 D 撰写会漏一处触发否决

### C · 评分项 ↔ 资料库差距矩阵
- 按权重展开（30/60/10 或项目实际权重）
- 每个评分细项一行：状态（Y/已具备 / P/部分具备 / N/尚未具备 / Y*/需复核）+ 缺口 + 建议 + **预计影响分值**
- 必含 4 列：评分项 → 状态 → 关键缺口 → 行动建议
- 资格否决项独立成段（影响整标的扣分项）

### D · 风险 / 疑点
按影响严重度排序，每条带"动作建议"：
- D.1 **致命风险**（不补会丢整标）：如业绩证明文件不全、专用资格要求细则未找到
- D.2 **重要风险**（会显著拉低分数）：如人员配置不齐、绿电证书缺、专利缺
- D.3 **商务/技术偏差表应答策略**：建议勾选 + 理由
- D.4 **"免收响应保证金"联动标注**（高频踩坑点）：列出三处必填位置
- D.5 **履约担保与价外不确定性**
- D.6 **价格下限与税务风险**（含 veto 4672 类的百分比红线）
- D.7 **实施地点冲突**（公告附件 vs 技术规范书）
- D.8 **评审期合规预警**（谈判期需备物品、纸质文件邮寄地址、代理服务费缴纳节点）

### E · 撰写顺序建议（直接喂给 D/E 子 agent）
- E.1 并发可行性矩阵：任务 → 是否可并发 → 阻塞依赖 → 优先级
- E.2 推荐启动顺序（Wave 1–N）：每 Wave 列出具体动作 + 谁负责
- E.3 时间建议（按响应截止日期倒推日历）

## Procedure（执行步骤）

1. `list_requirements` → 拉全要求清单
2. **若数据 > 50KB**：用 `read_file` 读 /tmp/hermes-results/call_*.txt 本地副本解析；**不要重复 list_requirements**（重复调用会再次下载超大 JSON 浪费时间）
3. 用 Python 把 requirement 按 `req_type` 分桶统计（doc_template / qualification / score_rule / tech_spec / 等）——本类项目典型分桶：doc_template 180+, qualification 50+, scoring 30+, score_rule 15+
4. **逐类抽取关键事实**：
   - qualification：通用资格 + 否决项
   - score_rule：评分公式、权重、维度上限/下限
   - tech_spec：5 大模块 / 4 层架构 / 人员要求 / 成果要求 / 验收 / 质保 / 知识产权
   - basic_fact：项目名/编号/限价/截止时间
   - contract_clause：付款 / 履约担保 / 知识产权 / 验收
   - reject_clause / veto_clause：否决条款全文
5. `list_project_materials` 拿到 file_id 列表 → `get_project_material_blocks(file_id, size=3)` 抽样首段判定材料类型（采购公告/采购文件/技术规范书/合同/注意事项/签章文件）
6. `get_template_outline` → 拿到 is_file_item=true 的主条目清单 + is_file_item=false 的子条目群
7. `list_assets` → `search_assets(supplier_name)` → `get_asset(asset_id)` → 列事实
8. **整理素材-事实-评分三角映射**：
   - 每个评分细项（C 节）追溯到具体 fact_key / 评分细则条款 / 招标文件原文坐标
   - 每个【待补充】项（A/B 节）必须能回答"补什么、从哪补、影响谁"
9. 整合五节报告，作为最终回复一次性返回

## Pitfalls（高频踩坑点）

- **`list_requirements` 数据太大**：可能 290KB~345KB。截断有两种表现：
  - (a) 落盘到 `/tmp/hermes-results/call_*.txt`（双层 JSON：外层 dict + `result` 内层 stringified list）→ `read_file` 读本地副本 + Python 解析
  - (b) 报「Full output could not be saved to sandbox」→ **本次没有落盘文件**。此时先扫 `/tmp/hermes-results/` 找**前序会话产物**（`reqs_<project>.json`、`material_match_summary_<project>.md`、`evaluation_<project>.json`、`parse_reqs.py` 等）——session 181 实测 `reqs_181.json`（604 条/501KB）直接可用，比对当日新增 req（如 4796-4801 坐标修正版）后用 `get_requirement` 补查即可
  → **两种情形都不要重复调用 list_requirements**（必再次截断，浪费 token）
- **`is_file_item=true` 主条目 vs 子条目容易数错**：本类项目典型是「**6+2=8**份 is_file_item」
  （份数按 get_template_outline 实际判定）——父 agent 给出的份数与实际不一致时，差异在 A 节显式声明；
  商务组 (四) 4512「补充文件」是主条目，但其下挂 16 个子条目（4403-4416 等）**不**算 is_file_item。
- **"免收响应保证金" ≠ "免响应保证保险"**：很多人混淆。
  - 响应**保证金**：现金 / 银行汇款 / 银行保函 — 免收（采购文件 3.4.1）
  - 响应**保证保险**：保险公司的保单 — 同样属于"响应保证金的替代形式"
  - 3.4.1 写"免收响应保证金" = 整组不适用，**4504 响应函第 3 条 + 4511 + 4512.1.1-1.4** 都要写"不适用"
- **实施地点冲突**：采购公告附表口径与技术规范书 §1.2 经常不一致（北京 vs 杭州），
  B/D 节都需标注；scope_of_work 类 requirement 会显式提示"需向代理机构澄清"
- **价格下限红线**：veto 4672 — 不得低于全部通过初步评审算术平均值的 50% / 低于次低 50% /
  低于最高限价 45%（下限红线按本项目实际限价计算）；实务合理价位由主会话按行情与成本测算自行判断，不预设区间
- **税率异常否决**：veto 4666 — 税率显示为 0 / 物资类项目税率为 6% / 不符合国家征收税率都否决；
  服务类一般 6%；软件类可能 13%；小规模纳税人可填 3% 或 1% — **写之前必须与企业税务身份确认**
- **业绩证明 = 否决高发地**：veto 4668 "只有业绩列表未附合同" → 整标否决；
  asset 库里的"XX 万元业绩"**不算业绩证明**，必须有合同扫描件 + 验收报告 + 对方盖章页
- **人员最小集合 ≠ 资料库列出**：技术规范书常规定最小人员配置（如本类项目 7 人：
  项目负责人 1 + 技术负责人 1 + 项目经理 1 + 工程师 4），但 asset 库常只列 2-3 人 — B/C 节必标差
- **"采购公告附件附表二" 经常 doc_block 未抽到**：project_meta 类 requirement 会显式
  标注"专用资质业绩要求内容未在已抽取的文本块中读到" → **必须**列入 D 节"必须外呼/索要"清单
- **应免收的不动 vs 应主动声明**：响应保证保险「如有」= 自选；免收时填"免收不适用"比留空好
  ——留空可能被评审误判为漏填
- **`search_knowledge` 端点常返回 401**（session 181 实测）：`/api/v1/knowledge/search` MCP 调用反复 `401 Unauthorized`
  → **不要再 retry，直接在报告中如实标注"知识库端点暂不可用，未检索任何历史项目"**
  → 把 asset_id 内的强相关 fact（如"某年某项目合同额业绩"）**明确归属为企业资料库事实，不可声称为"知识库命中"**
  → 知识库维度的"交叉引用"任务**降级为可选**写入建议下一步，**不要杜撰历史项目**
- **`vision_analyze_minimax` 对某些 PDF 会 422**（session 181 实测 对应文件 国家电网签章 sign 文件）：
  → 签章文件 / CSYV 编号的 PDF / 仅含图像的 PDF 经常 422
  → **fallback**：用 `get_project_material_blocks(file_id, size=3)` 取首段文本判定文件类型即可，不必依赖 vision 工具
  → 报告中材料清单行可写"vision 接口 422；按文件命名规范判定为 XXX"
- **`is_file_item=true` 字段可能未在 `structured` 中显式标记**（session 181 实测）：
  → 不能机械按 `structured.is_file_item` 过滤找固定份数主条目
  → 商务组 4512 补充文件下挂的 16 个子条目（4398-4416）也按 role/order 字段识别，不依赖 is_file_item 标志
- **数据规模修正**：session 181 实测 `list_requirements` 返回 **604 条 / ~334KB**（不是之前的 554 / 290KB 估算）
  → 全部 req_type 数量分布变化不大（doc_template 208 / qualification 58 / scoring 45 / compliance 29 / technical_spec 21 等）
  → 数据规模判断应按 **req_count > 300 → 本地副本解析** 的固定阈值触发，不要硬编码 554
- **父 agent 报"is_file_item N 份"必须自行核对**：session 181 某任务（gap-report 实战）父 agent 在 prompt 里说
  "is_file_item=true 7 项"，但 `get_template_outline` 实际返回 8 个（4504/4507/4508/4510/4511/4512/4522/4523）。
  → **绝不能**机械按父 agent 的数字写 — 必须自己过滤 `is_file_item=true` 全集核对
  → 差异在 A 节显式声明"父 agent 报的份数与实际不一致，本报告按实际份数展开"（默认 A/B/C/D/E 结构里 A 节说）
  → 漏一份主条目会导致下游 D 撰写少传一份 docx，触发否决风险
  → 国网类项目典型分布是 **价格 2 + 商务 4 + 技术 2 = 8**；如父 agent 说 6/7/8 都要自己核
- **`get_project_material_blocks` 分页是偏移量制，不是页码**（session 181 某任务 实测）：
  → `page` 参数含义 = offset 页码：`offset = (page-1) × size`（page=1&size=50 → block_index 0-49；page=14&size=100 → 1300-1386）
  → 定位评分标准原文等段落时：先用 requirement 的 `coordinates.block_index` 反推 `page = block_index // size + 1`
  → 不要按 PDF 页号猜 page（同一 page 参数在不同 size 下对应完全不同的区间）
  → **off-by-one 静默错区**（某任务 实测）：心算 size 与实际传参不一致（按 size=30 算 page、却传 size=40）
  会返回**另一段同样长得合理的表格区**——同一文档里权重表/评分细则表有多份拷贝、内容高度相似，
  必须核对返回**首项 block_index** 是否命中目标块，绝不能靠「内容像不像」判断取对没有
- **成果审计三硬伤（gap 报告必查项，某任务 实锤抓到 2 处真错）**：
  ① **财务年份核对**：成果正文写「近三年 2022—2024」但采购文件要求 2023—2025（commercial_clause 4713 类 req）→ 必须把 basic_fact/commercial_clause 里的年份要求与成果正文逐年比对，不一致即报硬伤
  ② **进度计划 vs 履行期限**：成果实施计划总时长（如 30+90+30+90=240 天）可能超出履行期限（如「至 2026-12-31」约 170 天）→ 逐日核对，超期即报冲突；另注意「验收与质保阶段」不能把 12 个月质保塞进履行期（质保应顺延至次年）
  ③ **报价单缺「折扣比例（％）」列**：doc_template 4170 格式为 包号|响应总价|折扣比例，报价单 sheets 常漏此列
- **混合税率报价**：服务项目含硬件行（软件 6% + 硬件 13%）属合法混合，但 D 节必须标注「税率口径须与纳税人身份一致，写前向客户确认」（veto 4666 红线：税率 0 / 物资类 6% / 不符国家规定均否决）；纳税人身份可给批注建议值「一般纳税人（按注册资本推断，需客户确认）」
- **【待补充】标签审计四级法**（某任务 实战方法论）：通读三份成果全部【待补充】标签，逐一归级：
  - **A 级·本可填实**（无需客户新资料）：人员配置（项目负责人=资料库已有人员，按岗位资格要求年限核对后填）、「如有」类填「无」（名称变更/联合体/凭证单）、纳税人身份批注推断值、传真填「无（电话/邮箱联系）」、自查表预填、不适用模板加注「本项目不适用」
  - **B 级·先搜后填**：股东信息先 `search_web_minimax` 搜公示系统/企查查，搜不到再归 C 级
  - **C 级·客户必供**（真实资料无法代填）：业绩合同三件套、授权书签章、信用查询报告、审计报告、关系说明、证书扫描件
  - **D 级·成果本体缺失**（连【待补充】标签都没有的缺件）：业绩情况表、基本情况表逐格、技术偏差表正文、详评指引索引
  → 报告里分级列出 + 每项带责任归属（成果 id + 章节号），下游 D/E 直接照单修
- **`search_assets` 的 query 不参与过滤，永远返回全库清单**（本项目 实测 1425 条/276KB，自动持久化到 /tmp/hermes-results/call_*.txt）：
  → 不要反复调用；用 python/grep 在本地副本上二次过滤（按项目目录段如 `03_本项目分包`、按目录命名提取事实：人员名单藏在 `06_人员与身份／NN_人名` 目录名里；业绩三件套按文件名后缀分组 `1.x.1合同 / 1.x.2发票 / 1.x.3发票查验` 计数）
- **`get_asset` 结构化 facts 常为空壳**（fact_value=文件名、status=1 未确认）：

### 默认结构（项目级 A/B/C/D/E 五节）

父 agent 通常按"项目级现状与差距"调用 → 默认采用 **A/B/C/D/E 五节**结构：

- **A · 关键素材清单与来源坐标**（材料表 + 资产表 + 评分细则核心数据 + 项目级系统提示）
- **B · 各份 is_file_item=true 文件的当前空缺项**（每份主条目单独建表 + 16 份子条目 + 免收响应保证金三处联动）
- **C · 评分项 ↔ 资料库差距矩阵**（30/60/10 全部展开 + 资格否决项独立成段 + 每行带预计影响分值）
- **D · 风险/疑点**（按影响严重度排序：致命 → 重要 → 商务/技术偏差策略 → 联动标注 → 履约担保 → 价格下限 → 实施地点冲突 → 评审期合规预警）
- **E · 撰写顺序建议**（并发可行性矩阵 + Wave 1-N 启动顺序 + 倒推日历）

**A/B/C/D/E 五节是不可合并、不可改名、不可省略的硬骨架**——下游 D 写作子 agent 与 E 验收子 agent 期望看到的就是这五节。

### 父 agent 自定义结构（高频模式 — 必须灵活适配）

父 agent 偶尔会**覆盖默认结构**，直接给一份"用户自定义 7 段式"输出框架。**必须遵守父 agent 给的格式**，但每段内部仍可借用 A/B/C/D/E 素材。session 181 实战（2026-08-23）的父 agent 自定义格式：

```
项目概况 / 材料清单 / 招标要求统计 / 企业资料匹配现状 / 知识库命中 / 差距与风险（招标人视角）/ 建议下一步
```

**操作要点**：
- 父 agent 自定义格式**优先于**默认 A/B/C/D/E —— 不能因为默认格式更"标准化"就拒绝父 agent 指定的格式

### 第六种高频格式（「某轮」 实战）：「A 阶段现状分析与证据取证」单文件落盘

父 agent 指定「现状分析+证据取证，产出 /tmp/p<proj>/A_分析报告.md，回复只给路径+关键结论摘要（≤400字）」时的结构：

```
一、采购口径锚点（资格/人员/财务/截图时效/评分细则，每条回挂采购文件原文出处行号）
二、逐张取证结果（每张图一张表：证书名称/编号/发证机构/标准范围/发证日期/有效期至/持证主体 + 证据文件路径；标题页/空白页照实记录）
三、专利可用性结论（权利人主体一致性 + 公开状态 + 技术主题相关性 → 可用/不可用 + 预计得分）
四、信用与合规文本归纳（每份材料：文本层状态 → 证据内容 → 有效期状态）
五、企业事实清单（每项带证据文件路径）
六、资质证书有效期与主体核验结论（覆盖截止日判定，过期/主体不符标红）
七、业绩与资格要求口径匹配分析（四步法，每项带匹配度 + 得分投影）
八、材料缺口清单（缺口/影响/处置方向）
九、风险清单（按严重度排序：资格级→得分级→合规级）
十、待主会话处置事项（客户实体动作/材料核对/口径确认/补取证/成文注意）
```

**操作要点**：
- 口径锚点表打头——资格/人员/财务/截图时效/评分细则每条回挂采购文件原文出处（行号），后续所有判断据此，不得凭记忆
- 逐张取证表字段固定七项（证书名称/编号/发证机构/标准范围/发证日期/有效期至/持证主体），覆盖判定一律对「首次响应截止日」而非今天
- 核验结论必须区分「OCR 噪声」与「主体不符」（判据=主体名称是否一致，见 Pitfalls）
- 缺口清单与风险清单每条都要落到「影响」（资格否决/预计分损）与「处置方向」
- 回复只给「报告路径 + 关键结论摘要」——摘要字数上限是父 agent 硬约束（本会话 400 字），长文全部写文件
