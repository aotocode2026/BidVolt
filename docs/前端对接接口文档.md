# BidVolt 前端对接接口文档

> 适用版本：2026-09-07 当前线上。
> 基址示例：`http://47.100.182.3:28123`。
> 所有接口路径带 `/api/v1` 前缀；鉴权方式统一为 `Authorization: Bearer <access_token>`。

---

## 0. 通用约定

### 0.0 本文档的内容和结构

本文档用于说明 BidVolt 前端对接所需的后端 HTTP 接口，结构如下：

1. `所有接口名单列表`：按模块列出全部接口路径和方法，便于快速查找。
2. `所有接口详细介绍`：按模块逐条说明接口路径、处理函数和主要用途，并附重点接口请求/响应示例。

### 0.1 鉴权与令牌

| 令牌 | 有效期 | 用途 |
|---|---|---|
| `access_token` | 2 小时 | 每次请求携带（Bearer） |
| `refresh_token` | 30 天 | 仅用于 `/auth/refresh` 换取新令牌对，换新后旧 refresh 立即作废 |

任意接口返回 401 时，前端应使用本地 `refresh_token` 调用 `POST /auth/refresh`，并用新令牌重试原请求一次；仍失败则提示重新登录。

### 0.2 错误约定

- 失败通常返回 `{"detail": "原因"}`。
- 状态码表达类别：401 未登录/令牌失效、403 无权限、404 不存在、409 状态冲突、422 参数错误。
- 前端应直接展示 `detail` 原文，服务端保证原因具体可读。

### 0.3 任务状态码

`1` 排队中 / `2` 运行中 / `3` 完成 / `4` 失败可重试 / `5` 已取消 / `6` 失败终态。

Agent 主会话任务的 `result.outcome`：

- `complete`：全部验收门通过
- `incomplete`：主会话判定未闭环，`result.reason` 给出原因

### 0.4 相关文档位置和作用

- **《接口更新记录》**：`docs/接口更新记录.md`
  - 记录接口的新增、修改、废弃等历史变化。
  - 按时间倒序或正序排列，包含更新时间、更新原因、关联 commit/issue/discussion 和注意事项。

- **《接口变更申请模板》**：`docs/接口变更申请模板.md`
  - 用于提交接口变更申请。
  - 需要新增或修改接口时，先按该模板说明现状、目标、必要性和约束。

### agent

#### POST /projects/{project_id}/agent-run

- 处理函数：`agent_run`
- 参数：`project_id: int, body: dict`
- 权限：`PROJECT_EDIT`
- 说明：提交Agent 主会话相关操作。

#### GET /projects/{project_id}/agent-run/{task_id}

- 处理函数：`agent_run_status`
- 参数：`project_id: int, task_id: int`
- 权限：`FILE_READ`
- 说明：获取Agent 主会话相关详情。

#### POST /projects/{project_id}/agent-run/{task_id}/asks

- 处理函数：`agent_run_ask`
- 参数：`project_id: int, task_id: int, body: dict`
- 权限：`ask_customer`
- 说明：ask_customer / report_customer_actions 工具：主会话向客户提问或上报提交前动作清单。
kind=question：items=[{q, need, checked}]（也兼容纯字符串）；kind=action：items=[str]。
MCP 调用 task_id 可传 0，服务端按 capability token 的 tid 解析。

#### POST /projects/{project_id}/agent-run/{task_id}/asks/{ask_id}/answer

- 处理函数：`agent_run_ask_answer`
- 参数：`project_id: int, task_id: int, ask_id: int, body: dict`
- 权限：`PROJECT_EDIT`
- 说明：客户回答主会话提问：落库 + 注入主会话（运行中排队注入，完成后直接对话）。

#### POST /projects/{project_id}/agent-run/{task_id}/chat

- 处理函数：`agent_run_chat`
- 参数：`project_id: int, task_id: int, body: dict`
- 权限：`PROJECT_EDIT`
- 说明：客户直接与主会话对话：向同一 session 追加一条消息，返回主会话回复。

#### GET /projects/{project_id}/agent-run/{task_id}/questions

- 处理函数：`agent_run_questions`
- 参数：`project_id: int, task_id: int`
- 权限：`FILE_READ`
- 说明：主会话向客户提的问题（ask_customer 工具）与提交前客户动作清单（report_customer_actions 工具）。
前端渲染问卡；客户答复走 POST /asks/{ask_id}/answer 回到主会话。

#### GET /projects/{project_id}/agent-run/{task_id}/stream

- 处理函数：`agent_run_stream`
- 参数：`project_id: int, task_id: int, since: int`
- 权限：`FILE_READ`
- 说明：会话控制台事件流：先补发 since 之后的历史事件，再实时推送新事件，任务终态后发 end。

#### POST /projects/{project_id}/pre-chat

- 处理函数：`project_pre_chat`
- 参数：`project_id: int, body: dict`
- 权限：`PROJECT_EDIT`
- 说明：任务前对话：项目尚无主会话任务时，客户先与 Hermes 聊天建立项目会话
（session 存 project.pre_chat_session_id）；之后 agent-run 会把任务 prompt
注入该会话，任务前的交代自动成为主会话上下文。

#### POST /projects/{project_id}/assembly/artifacts/{artifact_id}/render-qa

- 处理函数：`render_qa_artifact`
- 参数：`project_id: int, artifact_id: int`
- 权限：`render_qa_docx`
- 说明：渲染质检：docx 产物 → LibreOffice headless 转 PDF → 逐页 PNG + 空白页/页数统计。
Hermes 用返回的 PNG 路径配 vision 抽查版面（表格跨页/图片方向/断页）。

#### POST /projects/{project_id}/assembly/artifacts/{artifact_id}/save

- 处理函数：`save_deliverable_file`
- 参数：`project_id: int, artifact_id: int, file: UploadFile, mode: str`
- 权限：`DELIVERABLE_EDIT`
- 说明：远端 Office 文件保存：
mode=overwrite 覆盖当前文件（覆盖前内容先归档，artifact_id 不变，version_no 递增）；
mode=new 另存为新版本（继承逻辑文件身份，旧版本保留）。

#### GET /projects/{project_id}/assembly/artifacts/{artifact_id}/versions

- 处理函数：`list_artifact_versions`
- 参数：`project_id: int, artifact_id: int`
- 权限：`FILE_READ`
- 说明：返回同一逻辑文件（`logical_file_id`）的版本链，按 `logical_version_no` 排序；每项含
  `artifact_id/name/version_no/logical_version_no/parent_artifact_id/bytes/created_at/updated_at/download_url`。

## 3. 文件与项目材料

### POST /api/v1/files/upload（multipart/form-data）
字段：`target` = `project`（项目材料）或 `enterprise`（企业资料）；
`project_id`（target=project 必填）；`files` = 一个或多个文件（**支持多选**）。

→ `200`：`{"files":[ {...} ]}`，单文件条目字段：
```json
{
  "file_id": 1799,
  "name": "xxx.docx",
  "size": 12345,
  "status": 3,
  "parse_status": null,
  "duplicate": true,          // 内容与库内相同（sha256 去重），file_id 指向既有文件
  "asset_id": 12,             // 仅 target=enterprise
  "auto_ingest": true,        // 仅 target=enterprise：自动入库分类+初始事实
  "facts_extracted": 5,
  "expanded": {               // 上传的是 zip：自动解包入库结果
    "imported": 3, "duplicates": 1, "failed": 0
  },
  "error": "原因"              // 该文件失败（其余文件不受影响）
}
```
要点：
- 压缩包**上传即自动解包入库**（内部文件成为项目材料/企业资产，原件保留）；嵌套 zip 递归展开（≤6 层）；
  `expanded.failed` 条目带包内路径与原因。
- 解析失败的文件会整体拒绝（`error` 给原因），不会留下"上传成功但用不了"的记录。

### GET /api/v1/files/{file_id}/image-descriptions（图片结构化描述清单）
→ `200`：
```json
{"file_id":1799,"image_count":47,"described_count":47,
 "items":[{"ordinal":0,"page":null,"sha256":"d76b...","described":true,
           "description":{"doc_type":"发票","subject":"...","numbers":["..."],"dates":["..."],"amounts":["..."],"people":["..."],"stamps":["..."],"text_summary":"...","is_scan":true,
```

## 4. Agent 主会话任务（端到端投标流程）

### POST /api/v1/projects/{project_id}/agent-run
```json
{"idempotency_key":"agent-<唯一串>","payload":{},"resume_from_task_id":1772}
```
- `idempotency_key` 必填（重复提交返回同一任务，`created=false`）。
- `resume_from_task_id`：沿用上一任务的会话继续跑（上一任务须有 `result.session_id`）。
→ `201`：
```json
{"task_id":1773,"status":1,"created":true,"resume_session_id":"20260830_...","progress":{...},"capability_token":"..."}
```

### GET /api/v1/projects/{project_id}/agent-run/{task_id}
→ `200`：
```json
{"task_id":1773,"task_type":"agent_pipeline","status":2,
 "progress":{"phase":"agent_pipeline","status":"running","percent":15,"current_work":"提问关已发起（0/1 组已答）…"},
 "result":{"outcome":"complete","reason":null,"session_id":"...","action_list":["盖章：..."],"customer_asks":[...]},
 "error":null,"customer":{"asks":[...],"action_list":[...]}}
```
- `progress.percent/current_work` 由真实里程碑驱动（5 启动 → 15 提问关 → 40-70 成文 → 85 打包 → 100 完成），页面 8 秒轮询。
- 终态（status∈{3,4,5,6}）按 `result.outcome` 渲染完成/未闭环/失败横幅。

### GET /api/v1/projects/{project_id}/agent-run/{task_id}/stream?since=N（SSE）
事件流（回放 + 实时，控制台数据源）：
```
event: message
data: {"seq":101,"kind":"hermes|service|user|tool|error","content":"..."}

event: end
data: {"status":3,"session_id":"...","outcome":"complete","reason":null,"action_list":[...],"last_seq":3641}
```
- `since=N`：从 seq>N 补发；结束后发 `event: end`。
- 终态任务会**按游标持续补读直到历史全部发完**再发 `end`（长历史 >200 条不漏尾部消息）；
  `end.last_seq` 是已补发的最后一条 seq，断线重连时前端用它作为新的 `since` 续传。
- 前端渲染建议：`kind` 着色区分（服务→主会话 / 主会话输出 / 客户→主会话 / 工具 / 错误）；
  控制台只渲染最近 N 条（如 2000），完整记录随交付包内 `会话记录/主会话记录.md`。

### GET /api/v1/projects/{project_id}/agent-run/{task_id}/questions（客户问卡）
→ `200`：
```json
{"asks":[{"ask_id":13,"kind":"question","items":[{"q":"...","need":"为什么需要","checked":"已自查"}],
          "answered":false,"answer":null,"created_at":"2026-08-30T07:21:55Z",
          "window_minutes":20,"timeout_notified":false}],
 "action_list":["盖章：授权委托书第X页加盖公章"]}
```
- **问答窗口**：每条提问有 `window_minutes`（默认 20）窗口；超时后服务端注入「由你自行决定」信号（`timeout_notified=true`），
  问卡**仍可补答**——补答会回传主会话回填重验。前端问卡须显示倒计时与「已超时（仍可补答）」状态。
- 多组提问全部展示（每组独立倒计时 + 独立提交）。

### POST /api/v1/projects/{project_id}/agent-run/{task_id}/asks/{ask_id}/answer
```json
{"answer":"1. …\n2. …"}          // 字符串整体一条；或 ["答1","答2"] 逐条对应
```
→ `200`：`{"ask_id":13,"answered":true,"queued":true,"reply":null}`
- 任务运行中：`queued=true`，回答经 **steer 插话通道**注入（R8 线上实证：主会话长轮次期间
  queue 模式会被 interrupt 忙时模式吞掉，steer 挂在下一个工具调用后注入，不依赖轮次边界）；
- 任务终态：走直接对话通道（`queued=false`，`reply` 为主会话回复）。

### POST /api/v1/projects/{project_id}/agent-run/{task_id}/chat（控制台对话）
```json
{"message":"...","mode":"queue","client_message_id":"cm-<uuid>"}
```
- `mode`：queue（默认，排队下一轮）| steer（插话，不打断，下一步工具调用后注入改方向）；
- `client_message_id`：可选（≤100 字符，超长 422）。客户端每条消息的唯一标识：同一标识重复提交**不重复执行**，
  直接回放原结果（`duplicate=true`）。

运行中（task 状态 1/2）→ `200`：
```json
{"queued":true,"mode":"queue","reply":null,"session_id":"...","message_id":88,
 "status":"queued","duplicate":false,
 "message":"消息已送达主会话：它正在忙手头这一步，做完马上读你的消息并回复（通常几分钟内，不用等整份标书完成）。回复见会话控制台。"}
```
- 运行中一律 `queued=true`（消息经泵循环注入长驻会话，不另起进程抢会话）；
- 终态任务：`queued=false`，同步执行并返回回复。

终态任务 → `200`：
```json
{"reply":"收到。我在。","session_id":"...","returncode":0,
 "message_id":88,"reply_to_message_id":89,"status":"processed"}
```
- `message_id` = 本条用户消息的 seq；`reply_to_message_id` = 对应回复事件的 seq（成功时二者不同，可用于关联）；
- `status`：`queued`（已排队）/ `processing`（同一 `client_message_id` 重试、原处理尚未落结果，罕见）/
  `processed`（回复完成）/ `failed`（运行失败）/ `no_valid_reply`（输出为空或仅含运行提示）；
- `failed` / `no_valid_reply` 时 `reply=null`、`error` 给出可读原因，且事件流会出现一条 `kind=error` 事件；
- `duplicate=true` 表示本次为同一 `client_message_id` 的幂等回放；
- 回复已剥离 Reasoning 框、会话尾注、框线与状态条噪音，不包含运行环境输出（Hermes 侧默认
  `display.show_reasoning=false`，见 `deploy/install-hermes.sh`）。

### POST /api/v1/projects/{project_id}/pre-chat（任务前对话）
```json
{"message":"现在都有哪些资料？","client_message_id":"pc-<uuid>"}
```
→ `200`：`{"reply":"项目共 5 份材料…","session_id":"2026...","returncode":0,
 "message_id":1,"reply_to_message_id":2,"status":"processed"}`
- `client_message_id`：可选（≤100 字符，超长 422）。同一标识重复提交**不重复执行**，
  直接回放原结果（`duplicate=true`）。
- `message_id` / `reply_to_message_id`：任务前对话消息的 seq 关联（成功时二者不同）；`status`
  取 `processed` / `failed`（运行失败，`error` 给原因）/ `no_valid_reply`（无有效回复）。
- 会话 id 存项目；之后点【开始】发起 agent-run 时，任务书自动注入该会话（交代成为主会话上下文）。
- 该阶段模型持**只读**业务工具（列材料/查资料库/查需求），能据实回答"有什么资料"。

### GET /api/v1/projects/{project_id}/pre-chat/messages?since=N&limit=200（任务前对话历史）

```json
{"project_id":207,"session_id":"2026...","since":0,"has_more":false,
```

### GET /api/v1/projects/{project_id}/response-package
→ 响应文件包 zip（**12 条目**：价格 3 + 商务 4 + 技术 2 + 内部管理文件 3
[报价测算工作簿.xlsx / 报价测算说明.docx / 编制逻辑与评分响应记录.docx] + 会话记录 2 + manifest.json）。
未打包时 409（detail 指引）；任务完成后由「下载响应文件包」按钮调用。
`manifest.json` 的 `audit` 字段（打包硬门禁全量信号）：
```json
{"checked":12,"coverage_ok":true,"unique_ok":true,"identity_ok":true,
 "missing_file_items":[],"duplicate_pairs":[],"identity_issues":[],
 "bare_pending":{},"bare_pending_count":0,
 "docx_quality":{"价格文件/（二）报价明细表.docx":{"tables":1,"pipe_paragraphs":0,"font_issues":0}, ...}}
```
- **打包硬门禁（服务端直接 409 拒绝，detail 列出文件与原因）**：
  ① is_file_item 条目未全部 seal 进包；②交付件存在竖线假表格（用 `|` 字符模拟表格）；
  ③字体违规（中文 run 缺 eastAsia 中文字体、或把 Calibri/Consolas 等西文字体设成中文字体）；
  ④编号冲突值（资料库 `numbers_conflict` 命中，如 S↔5 形近误读未处理）；
  ⑤17 位统一社会信用代码变体（91 开头应为 18 位）；
  ⑥报价测算说明/工作簿出现「上修」字样。
- 主会话须修复后重新打包；前端把 409 的 `detail` 原文透出即可（例如「交付件存在竖线假表格…」）。

### 服务端硬验收门（Agent 主会话的交付验收定义，主会话在包内自查 + 服务端打包兜底）
- **深度门**：技术专项响应文件正文 ≥100,000 字 / 大纲 ≥600 条 / media 图 ≥400 张 / 表 ≥50 个；
  商务补充文件正文 ≥35,000 字 / 图 ≥300 张；结构按本项目技术规范书与评分标准成文（不预设项目专属结构）；
- **报价反算门（客户策略口径驱动）**：A2（有效投标人评标价均值）估计口径由客户在**提问关选择**——
  限价锚定（有最高限价时 A2=限价原值）/ 样本锚定（A2=同形态样本中位）/ 保守取低（A2=最低同形态样本），
  未答默认限价优先；测算说明须**单行列明**最高限价（如有）/ A2 估计值 / 基准价 B=A2×0.98 / 最终报价
  四行数字；服务端校验 B=A2×0.98 算术、报价在 B 下方取整（不高于 B+1 万、不偏离 B 超过 2 万）、
  ≤限价、>异常低价红线、>成本底线，并按客户口径核对 A2（限价锚定时 A2 必须=限价）；
  禁止成本×系数=报价写法；无最高限价项目不受 A2=限价约束；
- **编号逐字 diff**：全包编号类字段与资料库原文并排比对零差异（优先 numbers_verified，冲突条目并列复核）；
  vision 误读变体禁止以任何形式入件（含「曾误读为」复述）；
- **打包内容门**：最终 zip 12 条目齐全（见上），报价单.xlsx 含「报价明细表」+「说明」两个 sheet。
